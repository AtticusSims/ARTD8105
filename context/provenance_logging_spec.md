# Provenance Logging Specification

> ⛔ **DO NOT EDIT THIS FILE.** It is replaced whenever you run `git pull course main`.
> Your own work goes in `my_work/`. To use a template, copy it there first.
> *If a pull ever fails with "local changes would be overwritten", you edited something in here.*

**ARTD8105 · v1.1 · 15 October 2026**
*How the agent records the work, so that students do not have to reconstruct it later.*

---

## The problem this solves

In the previous cohort, students were asked at the end of term to *"give one specific example of something you rejected from an AI tool's output."* Four students answered. Three of them did not answer the question — one described a limitation, one gave five words, one answered the opposite question. **The entire evidence base for whether students curated AI output rather than accepting it rested on a single student.**

That was not a student failure. It was an instrument failure. Asking someone in May to recall a specific rejection in March asks them to reconstruct something they never recorded — and the reconstruction will be smoothed, flattering, and wrong.

**So the recording happens at the moment, as a side effect of doing the work.** The student does not compose log entries by hand. Root `AGENTS.md` and the always-applied Cursor rule `.cursor/rules/10-research-log.mdc` instruct the agent to start logging automatically, without a separate student request.

**Automatic by default, checked on disk.** Rules instruct an agent; they are not a background recorder of every Cursor conversation. The agent must create or resume the session file, append each substantive exchange and verify the write. If tools or context are unavailable, it reports the gap. The student still checks the weekly summary and pushes the work.

**The log is submitted as part of the assessment.** It is a graded coursework artifact, collected at the end of term. That is what gives it weight and it is why the ritual holds.

This produces three things at once:
- **Evidence of authorship** the student can point to under questioning
- **Data for the study** with real timestamps rather than recalled ones
- **A process record** the student analyses in Step 8 to find their own findings

## The session workflow

**At the start of every student working session**, the agent reads this spec and inspects the existing logs. It creates or resumes this chat's session file in `my_work/_research_log/sessions/` without asking the student to start logging. A session means a period of work, not a numbered class. Resume only the same chat and working session; use a unique filename suffix if another session already has that date and minute. The `session` field must match the filename stem.

If the student has legacy logs at the repository root, read them for continuity. Do not move or overwrite them automatically. New records use the canonical `my_work/` location. If the workbook step is unknown, use `NA`; never postpone logging while waiting for it.

**At any point**, to check the agent has not drifted:

```
LOG CHECK
```

The agent must reply with the number of exchanges logged this session, the
turn numbers of any exchange with no disposition record, and whether the
session file exists on disk. If the numbers look wrong, tell it to write
catch-up records marked `"reconstructed": true`.

**At the end of every session:**

```
Close the logging session: write any outstanding disposition records, then
git add, commit with the step tag, and push.
```

**At the end of every teaching week:**

```
Generate this week's research log summary per the spec.
```

Read it. File corrections. Tick the review box.

The start instruction is no longer required. `LOG CHECK`, closing the session and the student's weekly review remain useful checkpoints. If the agent stops logging mid-session, catch-up records must be marked as reconstructed rather than silently backdated.

## Directory structure

Created in the student's project workspace at first session:

```
my_work/_research_log/
├── sessions/
│   └── 2026-09-03_1014.jsonl        one file per session, append-only
├── decisions/
│   ├── DEC-001.md
│   └── DEC-002.md
├── weekly/
│   └── WK-03_summary.md
└── INTEGRITY.md                      auto-generated checks
```

**All logs are append-only.** Never edit or delete a record. Corrections are new records of type `correction` that reference the original by `turn`.

## Record type 1 — `exchange`

Written by the agent **at the end of every substantive turn**, appended as one line of JSON to the current session file.

A turn is "substantive" if the agent produced anything the student could act on. Greetings, clarifying questions, and file-loading confirmations are not substantive and are not logged.

```json
{
  "type": "exchange",
  "ts": "2026-09-03T10:14:22+08:00",
  "session": "2026-09-03_1014",
  "turn": 7,
  "workbook_step": "S4",
  "move": "verify",
  "student_intent": "check whether the reaction-diffusion claim in my draft is supported",
  "agent_output_kind": "citation_set",
  "artifacts_touched": ["draft_intro.md"],
  "citations_offered": 4,
  "citations_verified": 2,
  "citations_dropped": 2,
  "flags": ["unverified_claim"],
  "agent_note": "two citations could not be resolved to a real source and were withdrawn"
}
```

### Field definitions

| Field | Values | Notes |
|---|---|---|
| `type` | `exchange` | fixed |
| `ts` | ISO 8601 with `+08:00` | Macau time; never omit the offset |
| `session` | filename stem | |
| `turn` | integer | increments within a session |
| `workbook_step` | `S1`–`S11`, or `NA` | use the stated step; if unclear, use `NA` rather than guessing or delaying the log |
| `move` | see table below | exactly one, the dominant move |
| `student_intent` | ≤ 20 words | the student's own words where possible, else your paraphrase |
| `agent_output_kind` | see table below | |
| `artifacts_touched` | array of paths | files read or written, workspace-relative |
| `citations_offered/verified/dropped` | integers | omit if no citations involved |
| `flags` | array, see below | omit if empty |
| `agent_note` | ≤ 30 words | only when something non-obvious happened |

### `move` values — exactly one per record

| Value | Meaning |
|---|---|
| `retrieve` | found literature, venues, prior art, documentation |
| `expand` | generated options, angles, lists to react to |
| `verify` | checked a claim or citation against a source |
| `critique` | assessed student work against a standard |
| `structure` | organised an argument, section order, figure plan |
| `draft` | produced candidate text (marked `[AGENT DRAFT]`) |
| `revise` | edited student text for clarity, grammar, idiom |
| `implement` | wrote or modified code |
| `debug` | diagnosed a failure in code or fabrication |
| `explain` | taught a concept, tool or convention |
| `redirect` | declined a request and offered an alternative |

### `agent_output_kind` values

`list` · `assessment` · `draft_text` · `code` · `citation_set` · `structure` · `question` · `explanation` · `refusal`

### `flags` values

| Flag | Raise when |
|---|---|
| `unverified_claim` | an `[UNVERIFIED]` or `[UNCERTAIN]` item was involved |
| `scope_drift` | the work moved away from the declared research question |
| `authorship_risk` | you produced text that could be pasted into the manuscript |
| `student_disagreed` | the student rejected your reasoning and proceeded differently |
| `venue_file_absent` | a quality judgement was requested with no venue file present |
| `venue_conflict` | your instinct and the venue file disagreed |
| `reconstructed` | this record was written late, not contemporaneously |

## Record type 2 — `disposition`

Written at the **start of the next turn**, recording what the student actually did with the previous output. This is the single most important record type in the system and the one the rubric's Curation criterion depends on.

```json
{
  "type": "disposition",
  "ts": "2026-09-03T10:19:47+08:00",
  "session": "2026-09-03_1014",
  "refers_to_turn": 7,
  "disposition": "modified",
  "note": "kept the two verified citations, cut the reaction-diffusion claim entirely rather than reframing it"
}
```

`disposition` is exactly one of:

| Value | Meaning |
|---|---|
| `accepted` | used substantially as given |
| `modified` | used after material change |
| `rejected` | not used |
| `deferred` | set aside for later |
| `redirected` | student changed direction in response |
| `unknown` | genuinely could not tell — use sparingly and never as a default |

**Infer the disposition from what the student says and does, and say what you inferred.** If they paste your list back with three items deleted, that is `modified`. If they say "no, that's not it" and start over, that is `rejected`. If you cannot tell, ask — one short question is cheap: *"For the log — did you use that framing, change it, or drop it?"*

Do not ask more than once per session. If the student finds it intrusive, batch the question at the end of the session instead.

## Record type 3 — decision records

When a disposition is `rejected` or `modified` **and the thing rejected was substantive**, write a decision record in addition to the log line.

Substantive means: it would have changed the research question, the contribution claim, the method, the venue, the structure of the paper, or the form of the artifact. Not: word choice, a single citation, a colour.

Write to `my_work/_research_log/decisions/DEC-NNN.md`, numbered sequentially:

```markdown
---
id: DEC-007
ts: 2026-10-14T15:32:10+08:00
step: S8
refers_to_turn: 23
disposition: rejected
---

## What was proposed
[Agent's suggestion, in enough detail to be understood later — 2-4 sentences]

## What the student decided instead
[The alternative taken]

## Stated reason
[The student's reason, in their own words. If they did not give one, ask
for one sentence — this is the one place it is worth interrupting for.]

## What this reveals
[Agent's one-line observation about what the decision shows about the
student's developing judgement. Optional. Mark clearly as agent inference.]
```

Expect roughly one to three of these per week during Steps 5–9. **A student with zero decision records by session 7 is not curating**, and the agent should say so directly: *"You have no decision records yet. Either you are accepting everything I produce, or we are not recording the moments where you don't. Both are problems."*

## Record type 4 — `correction`

Because logs are append-only, corrections are new records:

```json
{
  "type": "correction",
  "ts": "2026-09-10T09:02:00+08:00",
  "session": "2026-09-03_1014",
  "corrects_turn": 7,
  "field": "disposition",
  "was": "accepted",
  "now": "modified",
  "reason": "student clarified at weekly review that they had rewritten the framing"
}
```

## Git as the independent timestamp

The agent log is written by the agent and could in principle be edited by the student. Git commits are machine-timestamped and much harder to fabricate convincingly.

**At the end of each workbook step, the agent runs:**

Inspect the diff and stage the relevant work and log files explicitly, preserving unrelated changes. Then commit with a message in this form:

```bash
git commit -m "S<step>: <short description> [log:<session>]"
```

If the workspace is not a git repository, initialise it in the first session:

Initialise git, inspect and stage the intended files, then commit as `S0: workspace initialised`. Do not sweep unrelated files into the first commit.

The `[log:<session>]` tag lets the weekly integrity check match commits against sessions. Commit at least once per session even if no step completed.

**Students: do not squash or rewrite history.** The messy history is the evidence.

Push only when the student requests it, to their own remote. Never push coursework to the shared course repository.

## Weekly summary and sign-off

At the end of each teaching week, the student asks the agent:

```
Generate this week's research log summary.
```

The agent reads the week's session files and writes `my_work/_research_log/weekly/WK-NN_summary.md`:

```markdown
# Week NN — 3–9 October 2026

Sessions: 4 · Exchanges: 61 · Decision records: 2 (DEC-006, DEC-007)

## Moves
retrieve 14 · verify 11 · critique 9 · implement 8 · expand 7 · revise 6 · structure 4 · debug 2

## Dispositions
accepted 22 · modified 19 · rejected 11 · deferred 6 · unknown 3

## Citations
offered 27 · verified 19 · dropped 8

## Flags raised
unverified_claim ×8 · scope_drift ×1 · authorship_risk ×2

## Artifacts touched most
draft_intro.md (14) · venue/eva-london-2027.md (9) · sketch_03.js (7)

## What changed this week
[3-5 sentences, agent's summary of the substantive movement]

## Anything the student should notice
[Agent's honest observation — e.g. "your rejection rate dropped from 24%
to 9% this week, which usually means either the work got easier or you
stopped pushing back."]

---
Student review: [ ] read  [ ] corrections filed
```

**The student reads it and files corrections.** That checkbox is a member-check — it is what lets the log be treated as validated data rather than as machine output the participant never saw.

## Integrity checks

Weekly, the agent regenerates `my_work/_research_log/INTEGRITY.md`:

- sessions logged vs. git commits in the same period — flag mismatches
- exchanges with no matching disposition record — flag if over 20%
- `reconstructed: true` records — count and list
- gaps of more than seven days
- decision records referencing turns that do not exist

The point is not policing. It is that a log with known, stated gaps is usable evidence, and a log that silently pretends to be complete is not.

## Submission and collection

**The research log is a graded deliverable.** It is assessed under AI Process Literacy — Provenance (D1), Curation (D2) and Reasoning with prompts (D3) in `context/assessment_rubric.md`.

**What students submit, session 14 — 25 November:**

- the complete `my_work/_research_log/` directory — sessions, decisions, weekly summaries, INTEGRITY.md
- pushed to their GitHub repository, with the instructor holding read access from session 1
- plus a one-page **log self-assessment**: total sessions, total decision records, any periods where logging lapsed and why, and the student's own honest note on whether the log reflects what actually happened

That last item matters more than it looks. A student who writes *"I stopped logging properly in weeks 9–10 while I was chasing a print failure, and reconstructed four entries afterwards"* has produced a more usable record than one claiming unbroken coverage. **Say so in class in session 1** — otherwise students will optimise for the appearance of completeness.

**The instructor collects at the end of term** by cloning all repositories (see `course/guides/git_and_github_setup.md`). No submission step can be missed, because the material is already pushed. Weekly clones during term give an independent snapshot that does not depend on anyone remembering to submit.

**Research use is separate.** The log is collected and graded as coursework. Whether any of it is analysed for research is asked afterward, once grades are final. The ethics brief governing that is instructor-facing and is not in this repository.

## Reliability — read this honestly

**The agent can still drift.** Long sessions, complex tasks and missing context can interrupt logging. Always-applied instructions make recording the default, but do not prove a file was written. Read-back checks, `LOG CHECK`, git history and the weekly student review make gaps visible.

Mitigations, in order of how much they carry:

- **root `AGENTS.md` and the always-applied logging rule**, which require the agent to start or resume logging on its own
- **read-back after each write**, which checks that the record exists and parses as JSON
- **`LOG CHECK`**, which surfaces gaps while the session is still live
- **the weekly summary and sign-off**, which surfaces gaps while the week is still fresh
- logging is instruction §0 of the agent file, before anything else
- the schema is small and the fields are short

**Students can edit the log.** They can. So can anyone falsify a lab notebook. Git history, the weekly sign-off, and oral spot-checks in class are the cross-checks. The design goal is not tamper-proofing; it is making the honest path the easy path — and making a marked gap cost nothing while a fabricated record costs a great deal.

**Do not grade on log volume.** A student who has a thin log because they worked mostly offline with paper and a plotter has not done worse work. What is assessed is whether the record supports the claims the student makes about their own process.

**Automatic capture is not neutral.** Knowing the log exists changes behaviour — students may reject things performatively, or avoid asking questions that look naive. Watch for it, name it in class, and treat it as a finding rather than a contaminant. It belongs in the paper's limitations.

## Reconstructing earlier chats

Use `course/guides/catch_up_research_logs.md` in each original Cursor chat. Work only from conversation history that is actually visible, or an export supplied by the student. Repository files and commits can corroborate actions; they cannot establish an unseen conversation, rejection or reason.

- Inspect existing logs, including legacy locations, and skip exchanges already recorded. Reuse a stable `source_chat` identifier and this chat's catch-up file on a repeat run; never create duplicates to increase the count.
- Every reconstructed exchange, disposition or correction has `reconstructed: true`. Exchange records also carry the `reconstructed` flag. Reconstructed decision files carry the marker in their front matter.
- `ts` is the actual recording time with `+08:00`, not an invented historical timestamp. Include optional `original_ts` only when the original timestamp is visible. Unknown original times stay unknown.
- Include `source_chat` and `source_turn`: the visible chat ID/title or a student-provided label, and the source message ID/position. Record the visible range if history is partial; do not claim to have recovered omitted turns. If no stable chat label is available, ask for one before reconstructing.
- Log every substantive exchange supported by the source, including actionable advice and failures. Record observed dispositions; use `unknown` when the outcome is not visible. Never invent acceptance, rejection, a reason, citation verification or tool execution.
- Existing logs stay append-only. Append corrections with references to the original record. Do not erase a contemporaneous record merely to replace it with a reconstruction.
- Update the integrity report to distinguish live and reconstructed records and list gaps. Reconstructed records belong to their source period when that period is known; writing them today must not make them appear to be live work done today. Preserve student review marks and leave new sign-off boxes unticked.

Reconstruction is an honest catch-up record, not a claim of contemporaneous logging. Do not create artificial sessions to fill teaching-week quotas, and do not paste credentials, raw participant data or entire private transcripts into the log. Use short, evidence-based summaries.

## Ethics and consent

**The log is a coursework artifact first.** It exists because the course assesses provenance and curation, and it would exist whether or not any research were happening. Students are told about it in session 1 and it is described in the syllabus.

**Research use is separate and consented separately, after grades are submitted.** No student's log may be analysed for research purposes without their consent given after the grade is final. A student who declines still keeps the log — it is theirs and it is assessed — but their data does not enter any study.

Nothing in the log should contain third-party personal data. If a student's work involves participants, that data lives under whatever ethics approval covers it, not here.

## Minimum viable version

If the full schema proves too heavy in practice, this is the irreducible core. Do not cut below it:

1. **timestamp + step + move + disposition** on each exchange
2. **decision records for substantive rejections**
3. **git commit per step**
4. **weekly summary with student sign-off**

Everything else is refinement.
